# attribution.md — How Every Agent Signs Its Work

> One rule: **anything an AI assistant produces carries its handle and its model
> tag.** Identities are defined in `REGISTRY.md`; this file says exactly where
> and in what format they appear. Binding on every model.

The formats below are chosen to be **greppable**. `git log --grep='Model: gemma'`
must answer "what did the local model change?" in one command — that is the
whole point of the scheme.

---

## 1. Commits

Conventional-commit subject (`company/engineering-standards.md`), then a blank
line, then the body, then the trailer block:

```
feat: add catalog category filter

Filters the preorder catalog by product category client-side; no schema
change. Categories come from the existing products.category column.

Workspace: preorder-store
Agent: @build/ember
Model: gemma-lmstudio (Gemma 4 E4B, LM Studio, local)
```

| Trailer | Required | Value |
|---------|----------|-------|
| `Workspace:` | yes | the ONE workspace slug from `company/registry.md` |
| `Agent:` | yes | your handle, exactly as registered |
| `Model:` | yes | `<model-tag>` + a parenthetical with the concrete build |
| `Co-Agent:` | when a second agent contributed | their handle |
| `Verified-by:` | on the commit that lands a checked change | the checker's handle |

Rules:

- **Never sign as an agent you are not.** If you are Gemma, you are not
  `@build/forge`.
- **Never remove another agent's trailer** when amending or rebasing.
- A **human** commit needs no `Agent:`/`Model:` trailer. Absence of a trailer
  means a person wrote it — so never omit yours, or you claim to be human.
- Git can do this for you locally:
  `git config --local commit.template .gitmessage` (see §8).

## 2. Pull requests

- **Title:** `[<role>/<callsign>] <summary>` — e.g.
  `[build/ember] Add catalog category filter`
- **Body:** use `.github/pull_request_template.md` unchanged, and add one line
  directly under the Goal section:

```
Produced by @build/ember [gemma-lmstudio] · verified by @qa/vera [claude-code]
```

- If the PR is a **cross-model** hand-off (one model built, another checked),
  say so explicitly. That is a quality signal, not noise.

## 3. Generated code files

A file **created wholesale** by an agent carries a provenance line in its
existing header comment — never a new banner block, and never a licence-style
preamble:

```js
/**
 * order-ref.js — generates human-readable order references.
 *
 * Generated by @build/ember [gemma-lmstudio] · 2026-08-02
 */
```

Rules:

- **Only on files created from nothing.** Do **not** stamp a file you edited —
  that misattributes the whole file to you. Edits are attributed by the commit.
- Do not update the line when someone else later edits the file. It records
  origin, not ownership.
- Never add provenance comments to **company documents** (anything under
  `documents/templates/`, `drafts/`, or `projects/`). Those are client-facing
  and their letterhead is fixed — attribution for those lives in the workspace
  `done-log.md` only.

## 4. Documentation and planning documents

Markdown that an agent authored ends with a one-line footer:

```markdown
---
*Drafted by @arch/sol [claude-code] · 2026-08-02 · see memory/decisions.md for rationale*
```

For a **planning document** (a plan, spec, or proposal), the footer goes at the
top instead, in a blockquote, so a reader knows before reading that it is
AI-drafted and unratified:

```markdown
> **Draft — @build/ember [gemma-lmstudio], 2026-08-02.** Not approved. Review
> against company/goals.md before acting on it.
```

## 5. Memory files

`memory/done-log.md` — one appended line per completed unit of work:

```markdown
- 2026-08-02 — BROLL-09: repriced Section B to 30 trips — by @build/ember [gemma-lmstudio] — verified by @qa/vera [claude-code]
```

`memory/decisions.md` — the existing format plus the deciding agent:

```markdown
- 2026-08-02 — decision — alternatives considered — reason — logged by @arch/sol [claude-code]
```

`memory/board.md` — cards carry `owner: @build/ember [gemma-lmstudio]`.

`memory/status.md` — no per-line signature; it is a snapshot, overwritten each
run. Note the model in the "Last updated" line if it matters for trust.

## 6. Changelogs and release notes

If a CHANGELOG is introduced, group by change, not by agent, and put the handle
at the end of the entry:

```markdown
### Added
- Catalog category filter on the preorder store (@build/ember)
```

Use the bare handle here — the model tag is resolvable via `REGISTRY.md` and a
changelog is read by humans, where terseness wins.

## 7. Inline code comments

**Do not** annotate individual lines with your handle. `// added by @build/ember`
inside a function is comment rot: it ages badly, survives refactors that
invalidate it, and git blame already answers the question better.

The only exception is a comment recording an agent-visible *constraint*, where
knowing which run discovered it is genuinely useful:

```js
// Chrome collapses a zero-font-size header template to nothing — found by
// @build/forge, BROLL-02. Do not remove the explicit font-size.
```

## 8. Optional: make git do it

Create `.gitmessage` (untracked, or committed with placeholders) and point git
at it once per machine:

```bash
git config --local commit.template .gitmessage
```

With `DOVA_AGENT_ID` / `DOVA_AGENT_MODEL` set in `.env.ai`, a shell helper can
append the trailers automatically. Keep this optional — a wrong automatic
trailer is worse than a hand-typed correct one.

## 9. What "unattributed" means

An unsigned commit or PR from an AI assistant is treated as **a defect**: the
checker should reject it and ask for an amend. This is not bureaucracy — with
four assistants writing into one repository, unattributable changes are how a
codebase becomes impossible to reason about, and how a bad pattern from one
model silently propagates through the others.
